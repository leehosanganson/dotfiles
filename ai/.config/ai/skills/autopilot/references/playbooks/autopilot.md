# Autopilot

**Trigger:** The user explicitly authorizes a sustained autonomous engineering run or multi-PR improvement cycle with a goal and completion criteria, including `/self-improvement`. An ordinary `/autopilot` implementation request does not select this playbook. Editing or discussing this workflow does not start or resume a run.

1. Clarify the target outcome, scope, verification, permitted repositories/branches, and stopping conditions. Invoke `/project-context`, then `/principle-outcome-oriented-execution` to split the goal into verifiable tasks. On resumption, check outstanding PRs with `/stage-deploy` before choosing new work; reconcile current scope and permissions rather than relying on old status or authorization from a previous session.
2. Choose the smallest fitting workflow: one task for a bounded run; independent PRs only for an explicitly approved multi-PR run. Use `/self-improvement` for roadmap selection when requested. Invoke `/plan` for each nontrivial unit and route it to its playbook in `references/playbooks/`.
3. Advance through reversible, authorized work without unnecessary pauses. Invoke `/show-me-your-work` at the start and after each verified unit. Invoke `/principle-prove-it-works` to verify each unit. Use `/stage-deploy` to publish and follow through for every new or resumed PR. Keep pending PRs tracked while independent authorized work proceeds.
4. Apply **Delivery policy** when starting or resuming the run. Use the resolved outcome for each in-scope PR, including bounded units of the run. If the outcome is merge, apply **Merge gate**. For PR-only delivery, stop at verified review readiness or a concrete blocker without asking to merge.
5. Stop the run and report when completion criteria are met, no independent safe work remains and outstanding PRs are complete or blocked, authorization is revoked, or the next step exceeds scope. Report outcomes, verification evidence, PR links and states, and remaining work. Leave unfinished PR todos open.

## Delivery policy

- **Self-improvement: merge by default.** An explicit user request to start or resume an Autopilot self-improvement cycle authorizes merging only that cycle's in-scope PRs into their intended, in-scope bases during the active session, subject to the merge gate. This covers new and outstanding PRs within the agreed cycle scope. If the user says PR-only, use review-ready delivery instead and do not merge. Honor any narrower limits or revocation.
- **Other sustained runs:** Merge remains a separately requested outcome and requires explicit scoped merge authorization for the active session. Otherwise stop at review readiness. Ordinary bounded Autopilot is unchanged: stop before merge.
- **On resume:** Keep the recorded outcome unless the current user request changes it. An explicit request to resume the self-improvement cycle supplies fresh scoped authorization under the rule above, unless PR-only applies. Keep an existing PR-only restriction unless the user lifts it. A handoff, compaction, or passive pickup does not itself grant new permission. If merge remains the outcome but no current grant covers an open PR, report an authorization blocker; do not mark it complete at review readiness.

## Merge gate

1. Confirm the active grant covers the repository, PR, and intended base. For merge strategy, use the settled user or repository method if allowed by the grant and current policy. If no method is settled, use the only enabled method if it is consistent with the grant. Other sustained runs still need explicit authorization covering the method. Do not ask for per-PR confirmation when scope, base, method, and permission are clear. If they are not, pause that PR and report the specific missing decision, permission, or policy evidence; ask only if a user decision is needed.
2. Immediately before merging, refresh provider state. Require the `/stage-deploy` readiness gates for the exact verified pushed head, the authorized base and strategy, current passing required checks and reviews for that head, and no drafts, conflicts, blocking findings, or unsatisfied policy gates. Merge authorization is not human review or approval of the diff. Wait for any required human review and branch protection or ruleset requirements; never supply or substitute approval on the user's behalf. If checks or reviews are pending, wait and recheck in the active delivery loop within the recorded budget and re-enter this gate. If the head or base changes, invalidate stale evidence and reverify in that loop before trying again. Do not merge if evidence is missing or a gate fails.
3. Use `/github-ops` for the GitHub merge operation; use the matching provider tooling elsewhere. Use an expected-head guard when supported. Otherwise recheck the exact head immediately before acting; stop if the provider cannot establish what would merge. Never bypass policy, use administrative overrides, enable auto-merge, or enqueue a merge, even if the provider command does so by default. If immediate merge is unavailable or cannot be established, report the blocker without issuing the command.
4. Verify with the provider that the intended PR and head merged into the intended base and report the resulting commit and state. Then reconcile the merged task work before completing delivery or cleaning up, as specified in `/stage-deploy`. If the result is uncertain, check live state before retrying and report the blocker if it cannot be verified.

**Boundary:** Sustained Autopilot authorizes task-scoped commits, branch publication, and PR creation. Merge authority is limited to **Delivery policy**. It does not authorize unrelated destructive, financial, security-sensitive, or otherwise irreversible actions. Neither the run nor a merge grant bypasses required checks or reviews.
